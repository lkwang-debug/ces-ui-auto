# 稳定性验收

优先保留有效断言，其次消除脚本波动，再评估速度。不删除节点、不降低断言、不以整条自动重跑、额外跳过或修改 Allure 原始结果获得通过。

## 执行和隔离

- 两个固定 Chrome 会话严格串行：业务管理与登录/改密验证隔离。改密的每次登录清除认证状态，不复用已登录结果冒充新密码验证。
- 同一环境、同一管理账号使用 Windows 执行锁，防止同时启动两轮造成互相干扰。
- 新增、修改、删除节点独立准备数据，fixture 和 finally 精确清理；清理失败必须失败。
- 原密码恢复和配置恢复仍走 UI 并验证；中断恢复文件按环境与账号隔离，不保存密码。
- 邮件通知沿用此前明确要求的保留策略时，新增用户、会议室和邮件配置单独记录为主动保留，不宣称所有数据已经清空。若测试负责人改为恢复清理，则按新的明确选择执行。
- 菜单根据实际授权与已登记别名解析；新增未登记菜单只在清单审计项失败，不阻断几十条无关前置。
- 白名单、SSO 本期只验证菜单可达，业务流程尚未自动化。人脸与高风险操作沿用现有排除策略，终端真实导入继续排除。

## 可靠证据

查询与删除等待本次请求结束、加载完成和表格稳定，已有空表不能证明本次删除成功。弹窗按活动层、标签和动作含义定位，错误采集用一次 DOM 快照避免重绘间隙元素失效。日期输入必须通过页面提交并验证实际字段值。

每次下载独立目录、独立监听；验证新文件完成、格式与内容，历史文件不能满足本次下载断言。用户、终端导出、日志、录制和备份仍执行真实下载。

异常恢复验证包含残留弹窗取消、额外表格列和嵌套按钮、登录输入重绘、下载目录异常恢复、假文件拒绝、没有新请求不能证明空结果、执行锁异常退出释放。运行：

```powershell
.\.venv-local\Scripts\python.exe -m pytest tests/unit --confcutdir=tests/unit -o addopts= -q
```

## 三轮与性能

先完成专项与乱序 CRUD 验证，冻结代码、配置及必要前置，再连续运行三轮全量。任何脚本修复后重新计三轮。每轮目录包含 manifest、收集节点、setup/call/teardown 耗时、独立 Allure、根因汇总及清理附件索引。

`verify_stability.py` 分别输出脚本稳定性、功能结果、前置齐备和性能达标；不得把它们合并宣称全绿。产品失败、服务失败与需求待确认保留原断言和证据。

修改前旧报告存在共享前置阻断，不能作为正式提速分母。必要前置齐备后，应建立相同覆盖的完整有效基线，使用 `--baseline` 比较。若基线有未解释失败、前置阻断或节点不同，不计算提速达标。缺少有效基线时，25%目标只能标记为待验收。

`--shuffle-seed` 用于额外乱序隔离检查。三轮正式全量不传测试文件或 `-k`，不同环境、选中节点减少或未执行节点不能计为提速成果。
